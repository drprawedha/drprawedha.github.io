Preamble

After successfully deploying WordPress behind an Ubuntu reverse proxy, another issue appeared unexpectedly. PHP-FPM refused to start even though the configuration syntax was valid. The service repeatedly failed during boot, preventing all PHP applications from running.

This investigation demonstrates how SELinux policies can affect network services even when Linux file permissions and application configurations appear to be correct.

Environment

  • Operating System: openSUSE 16
  • Web Server: Nginx
  • PHP Version: PHP 8.x
  • PHP Backend: PHP-FPM
  • Security: SELinux (Enforcing)
  • Reverse Proxy: Ubuntu Nginx

Problem Symptoms

Cockpit displayed the PHP-FPM service as failed immediately after startup. 

php-fpm.service
Failed with result 'exit-code'

Running the systemd status command produced the following message: 

ERROR: unable to bind listening socket for address
127.0.0.1:9001

Permission denied (13)

ERROR: FPM initialization failed

Since the configuration itself appeared valid, the next step was to inspect the operating system security logs.

Investigating the Failure

System logs confirmed that PHP-FPM was unable to bind to TCP port 9001. 

sudo systemctl status php-fpm.service

The service returned exit code 78, indicating that initialization failed before PHP-FPM could start listening for incoming requests.

SELinux audit logs revealed the actual reason: 

sudo ausearch -m AVC -ts recent

avc: denied { name_bind }

comm="php-fpm"

src=9001

tcontext=tor_port_t

Root Cause Analysis

SELinux classified TCP port 9001 as tor_port_t, a security label reserved for the Tor service.

PHP-FPM operates under the httpd_t security domain. Because the SELinux policy does not allow HTTP services to bind to ports labeled as Tor ports, the operating system blocked PHP-FPM before it could start.

This explains why Linux permissions appeared correct while the service still failed with "Permission denied".

Resolution Options

Two possible solutions were identified.

Option 1 — Use the Default PHP-FPM Port

Modify the PHP-FPM pool configuration to listen on the standard port: 

127.0.0.1:9000

This option requires no SELinux policy modification and is the recommended approach for single-server deployments.

Option 2 — Allow Port 9001 for HTTP Services

If port 9001 must be retained, its SELinux label should be updated: 

sudo semanage port -m -t http_port_t -p tcp 9001

After modifying the policy, PHP-FPM can successfully bind to the port without disabling SELinux.

Verification

After correcting the port configuration or updating the SELinux policy, PHP-FPM started normally. 

sudo systemctl restart php-fpm

sudo systemctl status php-fpm

Once the service became active, Nginx resumed forwarding FastCGI requests successfully and WordPress operated normally behind the reverse proxy.

Lessons Learned

  • SELinux policies are independent from Linux file permissions.
  • A "Permission denied" error does not always indicate incorrect ownership or file modes.
  • Audit logs provide far more useful information than application logs when SELinux blocks a service.
  • Always verify SELinux port labels before assigning custom service ports.
  • Keeping SELinux enabled is preferable to disabling an important security layer.

Conclusion

This troubleshooting exercise reinforced the importance of understanding Linux security mechanisms beyond basic service configuration. Rather than disabling SELinux to make the service work, identifying the underlying policy conflict resulted in a cleaner and more secure solution.

The experience also demonstrated how Cockpit, systemd, and SELinux audit logs complement each other when diagnosing infrastructure problems on enterprise Linux systems.
